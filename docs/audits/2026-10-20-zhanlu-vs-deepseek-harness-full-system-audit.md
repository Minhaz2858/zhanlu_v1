## 1. Executive Summary

Zhanlu has grown into a feature-rich agent platform (ReAct orchestrator + Synexia FSM + NL2SQL pipeline + ~190 tools + skills + MCP + swarm), but the audit found **four systemic weaknesses** that explain most of the end-to-end pain you have experienced:

1. **No enforced execution boundary.** There is no central tool-level wall-clock timeout, output cap, or audit trail. Every handler decides for itself; the registry's caps are decorative. A single failure re-runs the full LLM pipeline at 5 stacked retry layers → the 5-6 minute turns you saw are structural, not incidental.
2. **Honesty gaps at every "fallback".** Schema-only NL2SQL reports success for never-executed SQL (the exact class you hit), automations can fabricate reports from memory ledgers (grounding gate absent on this tree), the no-data finalize path emits a polished empty report, and a failed final DB commit still emits `done` — the user sees an answer that was never persisted.
3. **Multi-tenancy is one RLS membrane with holes.** Org isolation rests entirely on Postgres RLS whose NULL-bypass is by design, while the entity API hardcodes `default-org`, 17 tables are deliberately outside RLS with no service-layer enforcement, skills are a global cross-tenant registry, and datasource credentials are stored **and served** in plaintext (live-confirmed).
4. **Duplicated orchestration stacks.** ReAct and FSM both run in production with two independent context assemblies; the flag story is dead (`SYNEXIA_FSM_ENABLED` is on, and `query_database` runs the FSM regardless). This is where dsh's single-driver + seam architecture is the starkest contrast.

**Confirmed live during this audit:** KB passwords plaintext in DB (`ff3a…`, `0Gg.…` prefixes, incl. warehouse KB `74c8d56d`); RLS = 127 policies on 144 public tables.

## 2. The dsh Reference — What "Good" Looks Like

dsh is a local developer harness, not a SaaS — the fair takeaways are its **architectural invariants**, not feature parity:

| dsh invariant | Zhanlu today |
|---|---|
| **Everything-is-a-plugin** (Cordis): no privileged core; every capability is a replaceable registration with reversible effects | Monolith: `routers/agents.py` is ~17k lines; loop behavior (heartbeat, wall-clock, dedupe, watchdogs) is inline code, not seams |
| **Append-only SessionEvent log** with versioned schema (`SCHEMA_VERSION`), render-and-replay, committed generations never overwritten | `chat_messages` rows mutated in place; assistant row written at `done` only; no event log; crash mid-stream = silent EOF |
| **One agent-loop driver** behind an interface, interceptable via `agent/*` events (`agent/turn-stopping` can cancel cleanly) | Two drivers (ReAct + FSM), both live; cancellation only partially wired (client disconnect cancels the batch task mid-commit) |
| **Guarded execution pipeline** in `core/tools`: one place enforcing scope, output caps, and policy for ALL tools | No universal enforcement; caps per-handler opt-in; MCP and skills bypass them |
| **Seams** (Service Definition + Provider + Consumer): swap sandbox/shell/fs provider and every consumer moves | Sandbox is an implementation detail, not a seam; silent host-subprocess fallback |
| **Session fork** at a turn boundary with seed; **deliverables** and **spill** as first-class subsystems | Fork is an audit-trail copy; large tool outputs have no spill story |
| **Skills/capabilities scoped per agent** (`isolate` realm) | Skills are a global filesystem registry, cross-tenant by design |

## 4. Structured Summary

**Code quality.** Feature velocity has outrun invariants: duplicated definitions in the registry, a 17k-line router doing loop/persistence/UI-contract work inline, string-matching tests, 14 broken tests in the active area, uncommitted multi-session changes stacked on one branch. The strongest code (probe + breaker shipped today, replan_policy, dedupe guard, compaction) is exactly where a single invariant was enforced — the pattern generalizes poorly because nothing structural forces it.

**Logic correctness.** The system is honest in the places that were debugged live (query_database wrapper, empty-rows, environmental-error classification) and dishonest in the places that weren't (FSM node fallback B1, ask_data_agent B2/B3, automation grounding D3, final-commit failure A6, zero-row report polish D3). The common root: **fallback paths write success**. dsh's append-only event log makes this class impossible — you can't log a fact that didn't happen.

**Architecture.** The monolith lacks seams: no central tool-execution policy (D4/D5), no durable session event log (C5), no provider abstraction for sandbox/shell, duplicated orchestration stacks (A5), tenancy enforced by one membrane with 17 deliberate holes and a hardcoded fallback constant (E2/E3/E4). Every dsh invariant in the table in §2 has a concrete Zhanlu counter-example above.

**Agent workflow (end-to-end view of one data question).** Turn opens → 7-9 sequential LLM stages (B5) → tool call that may box an entire second FSM run with its own context assembly (A5) → if anything fails, 5 retry layers re-run all of it (A4) → if the DB is down, only one of the two data tools fails fast (A2) → if the final commit fails, the user still sees `done` (A6) → if the process dies, the frontend persists an empty bubble (C1). The pipeline produces correct answers when healthy (proven: correct Oct 12-18 window, ¥16.36M across 15 orders) — the defects are concentrated in **failure handling and boundaries**, precisely where dsh concentrates its abstractions.
