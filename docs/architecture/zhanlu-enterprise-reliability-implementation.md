## 2. Implemented fixes (Phase 3/6, all P1, all root-cause)

### B-3 — silent 200-row truncation in `ask_data_agent` (contract: tool → structured observations)
`delegation_tools.py` — the `ASK_DATA_MAX_RETURN_ROWS` slice now flags itself: `data_quality.result_truncated`, `total_row_count` (captured), `returned_row_count`. Existing `row_count` semantics unchanged (no consumer break).

### B-2 — single bound KB auto-resolve (contract: delegation → tool permissions → execution)
When the caller passes no `data_source_id` and EXACTLY ONE bound database KB exists, it is auto-resolved into the sub-loop context (the `db_tools._require_kb_id` seam already consumes it). Multi-KB ambiguity still defers to the sub-LLM; file/memory KBs excluded.

### B-1 — pre-flight warehouse probe on the `ask_data_agent` path (contract: failure → classification → bounded recovery)
Reuses the exact `query_database` probe (`_preflight_bound_datasources`, same `NL2SQL_PREFLIGHT_PROBE_ENABLED` flag, same breaker cache). Dead warehouse → immediate `success=False, error_kind="datasource_unreachable"` with zero LLM calls, instead of burning the 4-iteration sub-loop.

### A-1 (partial) — inner LLM call bounded by remaining wall-clock budget
The sub-loop's `_call_llm_with_retry` is now wrapped in `asyncio.wait_for(timeout=max(1, remaining_budget))`; on breach → `truncated=True` (honest partial data), not a hang. This also turned the stale pre-existing test `test_llm_call_in_delegation_has_timeout` green (it encoded this exact expected fix).

### A-2 — AgentApp-aware delegation + binding inheritance default ON
`DELEGATE_AGENTAPP_AWARE=True`, `DELEGATE_INHERIT_BINDINGS=True` (both fixes were tested but inert; rollback = env flag). This is the enabling change for cross-department scenarios A–E.

### A-6 — approval-paused activity step closed
Backend: every still-`running` activity step is flipped to `awaiting_approval` and re-emitted immediately before the v3 `paused` frame. Frontend: `ActivitySteps.jsx` knows `awaiting_approval` as a terminal status (ShieldAlert styling) — no permanent spinner.

### E-1 — MobileChatPage answer-lifecycle parity
`applyDelta`/`pendingReset` (D5), `content_reset` handling, `applyContentReplace` with invariant-I1 empty-rejection, `answer_persisted`/`backendOwnsContent` (D4 single-writer). No new mechanisms — the shared `answerLifecycle` helpers.

### E-3 — error text no longer persisted as an assistant row
Legacy `handleSend` catch path now renders the friendly error in the EXISTING placeholder bubble client-side only; no second assistant row is created (duplicate-message class eliminated).

### C-1 — evidence validation wired into capture (contract: tool results → evidence → provenance)
`record_turn_evidence` now verdicts each captured item with the pure Phase-2.5 validators (`validate_query_result`) under `EVIDENCE_VALIDATION_ENABLED=True` (new flag, fail-open to the previous "unvalidated" behavior). Items carry `validated`/`partial`/`invalid` + bounded issue limitations — the evidence surface is no longer "everything unvalidated".

### I-7 (found by the acceptance suite, promoted to fix) — reviewer verdict could fake completion
**Root defect:** `decision_from_review` zeroed all reviewer gap fields except the one matching `recommended_next_action`; a `needs_revision` review whose primary action was `revise_response` (or any verdict-level revision with no structured gap fields) reached the observation table as a CLEAN SUCCESS → decided **"complete / objective_satisfied"**. Contract 6 (evidence → reviewer → execution decision) silently converted revisions into completions.
**Fix:** all derived gaps now flow onto the observation, and the completion branch is overridden whenever `should_replan=True` — nuanced branches (`delegate_specialist`, `request_peer_collaboration`, `replan`) are preserved. This also repaired the two pre-existing `test_manufacturing_acceptance.py` failures, which encoded the same dishonest-completion class.

## 6. Architecture correction applied (2026-11-01): Projects, not Departments

The milestone's scenario/agent fixture was originally framed with departments.
Per the architecture decision, **Projects are the business-context and resource
boundary**; no Department layer is introduced. Changes made:

- **Acceptance suite reframed** (`tests/test_enterprise_acceptance.py`): agents are
  reusable capabilities with project memberships (the five automobile PROJECTS);
  selection assertions check capability relevance + PROJECT AVAILABILITY, not
  department membership. Shared specialists (e.g. `inventory_agent` serving
  Manufacturing Operations AND Executive BI) are first-class.
- **New §6 boundary tests against REAL enforcement** (sqlite in-memory):
  org wall (cross-org denied even for admins), `use`-share vs `view`-only semantics,
  fail-closed authorization, KB-membership isolation with authorized link-row
  sharing and foreign-org link immunity, `ProjectAgent` multi-membership,
  conversation/session project identity.
- **P0 fixed under the new architecture:** `_list_available_agents` discovery
  directory was org-unscoped (cross-tenant leak of agent metadata) — now scoped to
  the caller's org (user → org, else conversation → org), legacy no-context callers
  warn + keep legacy behavior. Tests: `TestDiscoveryOrgWall`.
- **Department remnants preserved** (load-bearing discovery metadata pinned by
  foreign tests) and frozen — see audit §9. Nothing new may depend on them.

Final principle: Organization = tenant isolation · Project = business context and
resource boundaries · Agents = reusable capabilities · General Assistant
coordinates. Test counts updated in the acceptance report
(`backend/reports/enterprise-acceptance-report.json` — 11 scenarios).
