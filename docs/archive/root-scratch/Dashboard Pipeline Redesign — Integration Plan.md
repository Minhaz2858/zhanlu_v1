**Project:** zhanlu (`/home/ysk2025/zhanlu_7_30/backend`)
**Date:** 2026-08-18

**Goal:** Replace the old dashboard-generation process with a pipeline where the agent uses the `ui-ux-pro-max` skill for design intelligence and builds a **full-stack dashboard app backed by real database data with live updates**.

---

## 1. Why the old process is being removed

| Old process | New process |
|---|---|
| Dashboard = a generated page/widget | Dashboard = a **full deployable app** (frontend + API + DB) |
| Static or mock data | Real data queried from the user's database |
| One-shot render | Live push updates (WebSocket/SSE, second-level) |
| Delivered once, then frozen | **Living app** — user keeps chatting to change design & data (Base44-style, §8) |
| Ad-hoc styling | Design system generated by `ui-ux-pro-max` reasoning engine |

The key mental shift: **a dashboard request is an app-build request with a design step in front of it.** The agent should never return a "dashboard-looking" artifact with fake numbers.

## 5. Realtime layer (FastAPI + live push)

**Default: WebSocket. Fallback: SSE** (simpler, auto-reconnects, works through more proxies — fine since dashboards are mostly server→client one-way).

```python
# backend/app/dashboards/<slug>/realtime.py
from fastapi import APIRouter, WebSocket, WebSocketDisconnect
import asyncio

router = APIRouter()

@router.websocket("/ws/{dashboard_id}")
async def dashboard_ws(ws: WebSocket, dashboard_id: str):
    await ws.accept()
    try:
        while True:
            # Poll the DB on an interval OR subscribe to a change event bus
            payload = await get_metrics_snapshot(dashboard_id)   # queries.py
            await ws.send_json(payload)
            await asyncio.sleep(2)   # second-level updates
    except WebSocketDisconnect:
        pass
```

Design rules for this layer:
- **Push on change, poll as baseline.** If your DB is Postgres, upgrade later to `LISTEN/NOTIFY` or a CDC tool (Debezium) so pushes are event-driven instead of interval polling. Start with 1–5s polling; it's fine for most dashboards.
- **Send diffs, not full snapshots**, once payload size matters.
- **One WS connection per browser tab**, server fans out to N dashboards.
- **Auth on the socket**: reuse your existing FastAPI auth dependency via the WS handshake (token in subprotocol or first message).
- **Backpressure**: if a client lags, drop intermediate frames — a dashboard should show the *latest* state, not queue history.

## 6. Data contract — the anti-fake-data guarantee

This is the most important behavioral change. Insert a mandatory confirmation step:

1. Agent introspects the target DB:
   ```python
   from sqlalchemy import create_engine, inspect
   insp = inspect(create_engine(conn_str))
   tables = {t: [c["name"] for c in insp.get_columns(t)] for t in insp.get_table_names()}
   ```
2. Agent proposes a **metric mapping** and shows it to the user:
   > "I'll show: daily revenue (orders.amount sum by created_at), order count, top 10 products. Refresh: 2s. OK?"
3. Only after confirmation does it write `queries.py`.

Hard rule for the agent prompt: **"If you cannot query real data, say so and ask — never invent plausible numbers."** This single rule is what makes the new pipeline trustworthy.

## 8. Conversational iteration — the Base44-style loop

The dashboard is never "finished." Like Base44, the user keeps chatting with the agent and the app keeps changing. This requires treating each dashboard as a **living project**, not a one-shot artifact.

### 8.1 The iteration loop

```
USER CHAT (in dashboard page, side panel)
   "make it dark mode" / "add monthly refunds" / "only show EU data"
                │
                ▼
EDIT INTENT CLASSIFIER  (agent decides what kind of change)
   ├─ DESIGN  → colors, fonts, style, density, dark mode
   ├─ DATA    → new metric, new filter, new table, different time range
   ├─ LAYOUT  → move/resize/reorder cards, add a page/tab
   └─ CONTENT → titles, labels, drill-down views
                │
                ▼
MINIMAL EDIT, not rebuild-from-scratch
   DESIGN  → update design-system/pages/<page>.md override, then theme tokens
   DATA    → edit queries.py (+ re-confirm metric mapping if new tables)
   LAYOUT  → edit the React page component only
                │
                ▼
REBUILD + LIVE RELOAD (Vite HMR / fast reload)
   User sees the change in seconds, in the same URL, no data loss
                │
                ▼
CHANGE SUMMARY + UNDO
   Agent replies: "Added monthly refunds chart (source: refunds table,
   2s refresh). Commit a1b2c3 — say 'undo' to revert."
```

### 8.2 What makes it feel user-friendly (non-negotiables)

1. **Chat lives next to the dashboard.** Split view: chat panel on the left, live dashboard on the right. The user watches changes land while typing — this is the core Base44 feeling.
2. **Every accepted change = one git commit** in the dashboard project. Free rollback, and the agent can answer "what changed yesterday?"
3. **"Undo" as a chat command.** `git revert` the last commit, reload. Non-technical users get safety without knowing what git is.
4. **Design edits persist via ui-ux-pro-max's master+overrides pattern** — the agent writes deviations to `design-system/pages/<page>.md` instead of one-off inline tweaks, so a later "make another page" stays consistent and a future session knows the decisions.
5. **Specific-space / specific-data views ("drill down in chat").** "Show me just Germany, last 30 days, by product" → the agent turns this into a **filter state or a new focused page**, validates the query returns real rows, and deep-links it (`?region=DE&days=30`) so the user can share exactly that view.
6. **Change preview for risky edits.** Small edits apply immediately; anything that changes the data contract or deletes a chart gets a one-line confirm ("This will replace the revenue chart with refunds — ok?").
7. **The no-fake-data rule applies to every iteration.** If a requested metric has no source table, the agent says so and proposes the closest real alternative.

### 8.3 Implementation notes

- **Session model:** one chat thread per dashboard, persisted (`dashboard_id → conversation history`), so context survives reloads and the agent remembers prior requests in the loop.
- **Build pipeline per edit:** keep the Vite dev server (or a fast rebuild watcher) running during the session; production builds happen on demand ("publish" button).
- **Concurrency:** lock the project during an agent edit; queue user messages sent mid-build and process them in order.
- **State separation:** keep *filter/view state* (user-controlled, instant, client-side) separate from *schema/design state* (agent-controlled, committed). "Show only EU" is a filter first; only becomes code if the user says "make this permanent."
- **Cost control:** cap the loop — e.g., max N automatic rebuilds per session without an explicit "apply" for large changes.

## 9. Persistence — saving to "My Files" as a living app

From the Acme AI screenshots: the platform already has an artifact system at `/my-files` with type filters (**Dashboard**, Report, HTML, PDF, PPTX, Markdown), project grouping (ACME BI, GLOBAL, MARKETING TEAM), Personal/Company scope, "Last Updated" sorting, and unread badges. The new pipeline must plug into this — the dashboard is saved there as a **living app artifact, not an exported snapshot**.

### 9.1 What "Save to My Files" means

When the agent finishes (or updates) a dashboard, it registers an artifact record:

```python
# DashboardArtifact — what My Files stores
{
  "type": "dashboard",              # shows under the "Dashboard" filter
  "title": "ERP Overview",
  "project": "ACME BI",           # sidebar project grouping
  "scope": "personal" | "company",  # From Personal / From Company tabs
  "owner_id": ...,
  "spec_ref": "dashboards/erp-overview@a1b2c3",   # git commit of the app
  "db_connection_ref": "vault://connections/erp-prod",  # NOT raw credentials
  "refresh": {"mode": "push", "interval_s": 2},
  "last_data_change_at": ...,        # drives "Last Updated" + unread badge
  "last_spec_change_at": ...,        # agent edits also bump "Last Updated"
  "chat_thread_id": ...              # the iteration loop (§8) resumes from here
}
```

Key difference from Reports/HTML/PDF artifacts: those are **files** (frozen at generation time). A Dashboard artifact is a **reference to a running app + data contract**. Storing a static HTML export of a dashboard would silently recreate the old process — forbid it.

### 9.2 Auto-update when the database changes

This is the "feels like a full app" requirement. Lifecycle:

```
SAVE (from chat)        → artifact registered, appears in My Files instantly
                          under "Dashboard", correct project + scope
OPEN (from My Files)    → backend attaches/starts the app instance,
                          runs queries.py against the LIVE database,
                          opens the WebSocket — user always sees current data,
                          never the data from when it was created
DB DATA CHANGES         → watcher detects change → pushes diff over WS to
                          every open viewer; updates last_data_change_at so
                          My Files shows fresh "Last Updated" + unread badge
APP SLEEPS (nobody      → instance scales to zero / stops; the artifact
viewing)                  stays in My Files; next OPEN re-attaches to live DB
                          (a dashboard with stale snapshot data is a bug,
                          not a power-saving feature)
USER CHATS AGAIN        → "add inventory chart" → iteration loop (§8) runs,
                          new commit → spec_ref bumps → artifact updated
                          in place, same entry in My Files
```

Change detection, in order of preference:
1. **Postgres `LISTEN/NOTIFY`** (or Debezium/CDC) — true event-driven push.
2. **Interval polling with change hash** (baseline, 1–5s): query, hash the result, push only on hash change — avoids spamming identical frames.
3. **Trigger tables** only if the user can't enable either of the above.

### 9.3 User-friendly behaviors that fall out of this

- **"My ERP dashboard" is a thing the user owns.** It sits in My Files next to their reports, opens in one click, and is always current — that's the "I made a full app" feeling.
- **Unread badge = data changed since you last looked.** Matches the existing "15 Unread" UI; gives users a reason to come back.
- **Personal vs Company scope** maps to sharing: Personal = only me; Company = teammates open the same live app (with the dashboard's WS auth respecting existing roles).
- **"Files in this task"** in the chat header shows the dashboard artifact while it's being built — the user can open it mid-conversation and watch the agent's edits land live.
- **Reopening the chat thread from the artifact** (and vice versa) — one click from My Files back into "keep editing this with the agent."

### 9.4 Backend work items

- [ ] Artifact registry: add `type="dashboard"` handling (registry currently stores files; add "app reference" artifacts with `spec_ref` + `db_connection_ref`).
- [ ] App instance manager: start/attach/stop dashboard instances on open/close; idle timeout → sleep.
- [ ] WS gateway multiplexing: one gateway routes `dashboard_id` channels to instances; auth via existing session.
- [ ] Secrets store for DB connections (never in the artifact record, never in chat).
- [ ] `last_data_change_at` updater feeding the My Files "Last Updated" sort + unread badge.

## 10. Acceptance criteria

1. Saying "make me a dashboard for X" triggers the new pipeline 100% of the time; old code path is unreachable.
2. The generated design system is persisted to `design-system/` and visibly applied (colors/typography match MASTER.md).
3. Every number on screen traces to a real SQL query — no mock data anywhere.
4. Inserting a row in the source table updates the dashboard within ~2s without refresh.
5. With DB unreachable, the agent asks for connection details instead of faking data.
6. After delivery, the user can keep chatting: a design request ("dark mode") and a data request ("add refunds") each land via live reload within seconds, are git-committed, and "undo" reverts the last change.
7. A chat request like "show only Germany, last 30 days" produces a real filtered view backed by a real query, shareable via deep link.
8. A later "add another page" stays visually consistent with the first, because design decisions persisted in `design-system/`.
9. A finished dashboard appears in My Files under the "Dashboard" filter, in the right project and scope (Personal/Company), within seconds of the agent finishing.
10. Closing the dashboard, reopening it a week later from My Files: it shows **current** database data, and a row inserted while it was closed is visible immediately — no stale snapshot.
11. A DB change while nobody is viewing updates the artifact's "Last Updated" and unread badge in My Files.
12. Chatting "add inventory chart" from the artifact updates the same My Files entry in place — not a duplicate file.

## 11. Risks & notes

- **Agent discipline is the weak link** — the design-doc rules must live in the system prompt, not just here, or the agent will regress to making pretty static pages.
- **DB credentials**: decide how users grant DB access (env var per workspace? secrets store?). Don't let the agent ask for raw passwords in chat if you can avoid it.
- **ui-ux-pro-max needs Python 3 only** — no network, no installs — so it's safe to run inside your backend container.
- Consider renaming `old_skills/` entirely; keeping a "new" skill in a folder named "old" will confuse both humans and future agent runs.
- **The iteration loop multiplies risk surface**: each chat message can touch code, data queries, and design. The git-commit-per-change discipline and the "minimal edit" rule are what keep a 50-message session from corrupting the app — don't skip them to save time.
- **Sleeping dashboards must never serve stale data**: the temptation to cache last-known data for closed dashboards recreates the old static process. The artifact is a reference to live queries; on open, always query fresh.
- **My Files currently stores files** — a Dashboard artifact is an app reference, so the registry, permissions, and previews all need a small conceptual extension (§9.4). Budget for it; it's the piece that makes everything else visible to users.
