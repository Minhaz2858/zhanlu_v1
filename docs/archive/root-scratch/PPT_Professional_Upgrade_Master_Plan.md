## 1. Hard Rules (apply to EVERY phase — learned from Phase 1/2)

1. **Plan first.** Write the phase plan, wait for explicit human approval, then code.
2. **Flag discipline.** Every new flag defaults `False` in `config.py` AND `.env.example`. Never commit `.env.example` with a flag `True`. Human enables flags in deployment config. Show `git diff` of `.env.example` as proof when config is touched.
3. **Strict tests.** Never weaken, skip, or relax a failing test to make it pass — fix the code. New behavior = new tests.
4. **No silent scope changes.** If a requirement can't be met, report it — do not downgrade it (e.g., "mandatory" must not become "optional").
5. **No deploys / no production changes** without explicit human go. Commits only when asked.
6. **Thumbnails are the review gate.** Every phase that changes rendering must regenerate the gallery (`scripts/regenerate_preview_gallery.py`) and present slide thumbnails for human visual review. "Tests pass" is never sufficient acceptance.
7. **One session = one phase.** Start a fresh session per phase; point it at this file + spec docs + memory notes.
8. **Timebox.** If any item exceeds 2× its estimate, stop and report — the human cuts scope, not the schedule.

## 2. Phase 3 — Theme Library 

**Goal:** 6 professional, visually distinct themes the user can switch between conversationally (`restyle_deck`), instead of one default look.

### Tasks

1. **Design 6 theme specs** (colors, font pairings, surface treatments) as data, not code:
   - `corporate_blue` (current default), `midnight` (current dark), plus new: `minimal_white`, `executive_slate`, `editorial_serif`, `vibrant_startup`.
   - Each spec: primary/secondary/accent palette (hex), background/surface colors, heading font + body font (system-safe fallbacks), KPI tile style, chart series palette (4–6 colors, colorblind-aware), table header/highlight treatment.
   - Store as JSON: `backend/app/services/artifacts/themes/<name>.json` + registry `themes/__init__.py` with `get_theme(name)` / `list_themes()`.
2. **Extend `build_pptx_templates.py`** to generate one `.pptx` template per theme from the JSON specs (keep byte-determinism; assert in test).
3. **Wire themes into the render path**: `ExportContext.theme_tokens` resolved from the theme registry by name; `restyle_deck(theme="...")` maps to registry names. Unknown theme name → clear error listing available themes.
4. **Planner awareness**: the planner prompt receives the active theme name + mood words so copy tone can match (e.g., `editorial_serif` → more narrative headlines).
5. **Gallery**: extend `regenerate_preview_gallery.py` to render the chatpath deck in ALL 6 themes (a "theme showcase" section in `index.html`).

### Acceptance

- `restyle_deck` works for all 6 themes in a live conversational flow; version history preserved.
- Theme showcase gallery reviewed by human (thumbnails).
- Contrast check passes on every theme (audit `contrast` check must pass — fix the palette, not the check).
- Tests: theme registry loads all 6; template generation deterministic; unknown theme errors cleanly; audit passes on every theme for the standard fixture deck.

## 3. Phase 4 — Deck Profiles 

**Goal:** structure follows intent. "Investor update" and "analyze my CSV" must produce fundamentally different decks.

### Tasks

1. **Define 4 profiles** in `deck_profiles.py`:
   - `data_report` (current behavior — default)
   - `executive_brief` — 3–5 slides max: cover → KPI grid → one chart_focus → key takeaways → closing. No raw tables; density budget halved.
   - `pitch_narrative` — narrative arc: hook → problem → evidence → ask. Section dividers between acts; headline style = story, not metrics.
   - `periodic_review` (weekly/monthly) — comparison-oriented: period-over-period deltas in KPIs, trend charts preferred over categorical.
2. **Router**: `deck_router.py` classifies user intent → profile (keyword rules + LLM fallback, 10s timeout). Explicit user instruction ("make it a pitch") always wins.
3. **Planner**: profile injected into the planner prompt; each profile constrains layout enum, slide count range, density budgets, and headline style. Schema gains `profile` field (additive).
4. **Fallback planner**: deterministic fallback must also honor the profile (no LLM → still correct structure).
5. **Tests + gallery**: one deck per profile in the gallery; per-profile unit tests on structure constraints (slide count, layout mix, density).

### Acceptance

- Same dataset, 4 different user intents → 4 visibly different deck structures (human reviews gallery).
- Profile classification: 90%+ correct on a 20-prompt test set the human provides.
- All existing Phase 1/2 tests stay green.

## 4. Phase 5 — Usage Instrumentation 

**Goal:** learn from real usage so quality decisions are data-driven.

### Tasks

1. **Event logging** (append-only table or structured log, whatever fits the codebase):
   - `deck_generated` — {artifact_id, profile, theme, slide_count, data_shape, llm_planner_used (vs fallback), audit_status, warnings[]}
   - `deck_edited` — {artifact_id, tool, slide_index, version_number}
   - `deck_downloaded` — {artifact_id, version_number, edit_count_before_download}
2. **Weekly digest query/script**: decks generated, edit-per-deck ratio, most-used edit tools, download-without-edit rate, fallback-planner rate (LLM timeout indicator), audit warn/fail distribution.
3. **Privacy**: log no slide content — only structure/metadata.

### Acceptance

- Events verified end-to-end (generate + edit + download in test → 3 events).
- Digest script runs and produces sane output on test data.

## 5. Phase 6 — Tier 2: Design-Freedom Renderer (est. 3–5 weeks; requires explicit human kickoff)

**Goal:** Kimi/Claude-level designed decks for requests that need them ("make it beautiful", pitch decks, external-facing).

**Read first:** `docs/superpowers/specs/2026-08-17-html2pptx-eval.md` (existing spike doc — update it, don't restart).

### 6.1 Design system foundation (week 1)

- Build the design system as machine-readable constraints: type scale, spacing scale (8pt grid), 12-col slide grid, component patterns (KPI band, quote block, image+text split, big-number, timeline, comparison).
- Assemble **10–20 world-class reference slides** (human provides; stored in `design/references/`) — the LLM imitates these.
- Deliverable: `design/system.md` + `design/components/*.html` exemplars. Human approval gate.

### 6.2 HTML slide renderer 

- LLM generates one HTML file per slide (1280×720) using the design system + components; rendered in headless Chromium at 2× → PNG.
- Conversion strategy (decide in spike, then commit): (a) full-bleed PNG per slide (pixel-perfect, not editable) or (b) html2pptx mapping to native shapes (editable, fidelity risk). Default recommendation: (a) for beauty tier, keep Tier 1 for editable tier.
- Gated by `HTML2PPTX_RENDERER_ENABLED` (default `False`). Router opt-in: explicit user ask ("designer deck") or profile `pitch_narrative` when flag on.

### 6.3 Vision QA loop 

- Feed rendered slide PNGs to a vision model with a rubric: overflow, alignment, contrast, empty-space balance, brand consistency. Score < threshold → targeted LLM repair → re-render (max 2 rounds).
- Wire into the audit pipeline as a Tier 2 check; mechanical audit still runs.

### 6.4 Unified editing 

- Conversational edits work on Tier 2 decks: DeckPlan still the source of truth; edits re-render affected slides only. One editing UX across both tiers.

### Acceptance

- Side-by-side gallery: same content, Tier 1 vs Tier 2 — human judges Tier 2 clearly superior on design.
- Vision QA catches seeded defects (deliberately overflowed slide → flagged and repaired).
- Edit flow works end-to-end on a Tier 2 deck with version history.
