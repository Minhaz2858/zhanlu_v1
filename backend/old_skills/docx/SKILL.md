# DOCX creation, editing, and analysis

## Overview

A .docx file is a ZIP archive containing XML files.

## Quick Reference

| Task | Approach |
|------|----------|
| Read/analyze content | `pandoc` or unpack for raw XML |
| Create new document | Write markdown to `outputs/` → emit `◤MD_DOCX◤` marker — see Creating New Documents below |
| Edit existing document | Unpack → edit XML → repack - see Editing Existing Documents below |

### Converting .doc to .docx

Legacy `.doc` files must be converted before editing:

```bash
python scripts/office/soffice.py --headless --convert-to docx document.doc
```

### Reading Content

```bash
# Text extraction with tracked changes
pandoc --track-changes=all document.docx -o output.md

# Raw XML access
python scripts/office/unpack.py document.docx unpacked/
```

### Converting to Images

```bash
python scripts/office/soffice.py --headless --convert-to pdf document.docx
pdftoppm -jpeg -r 150 document.pdf page
```

### Accepting Tracked Changes

To produce a clean document with all tracked changes accepted (requires LibreOffice):

```bash
python scripts/accept_changes.py input.docx output.docx
```


## Choosing a Document Type

**Pick the right type BEFORE writing any content.** Each type has a fixed structural template — a memo doesn't have a table of contents, a proposal doesn't have meeting minutes. Forcing content into the wrong template is the #1 reason an agent-generated DOCX looks unprofessional.

### The 5-type rubric

Answer these 4 questions in order. Each answer pins a type.

1. **Audience** — internal team, external client, executive, or public?
2. **Purpose** — inform (memo/report), request action (proposal/letter), record decisions (minutes)?
3. **Lifetime** — one-time read or persistent reference?
4. **Formality** — board-formal, business-casual, or friendly?

| Type | When to use | Key sections | Pipeline |
|---|---|---|---|
| **Memo** | Internal team, single-topic, ≤ 2 pages | Header (To/From/Date/Subject) → Body (≤ 3 sections) → Action items | MD → DOCX (simple) |
| **Report** | Multi-section, data-driven, 5-30 pages | Cover page → TOC → Executive summary → Body (with H1/H2/H3) → Appendix | HTML → DOCX (styled) |
| **Letter** | External client, formal request/notification | Sender block → Date → Recipient block → Salutation → Body → Sign-off | MD → DOCX (simple) |
| **Proposal** | External client, requesting approval/budget | Cover → Executive summary → Problem → Solution → Timeline → Budget → Risks → Next steps | HTML → DOCX (styled) |
| **Minutes** | Meeting record, persistent reference | Header (Meeting/Date/Attendees) → Agenda items (one per section) → Action items (table) → Next meeting | MD → DOCX (simple) |

### Structural template per type

Each template below is the minimum viable structure. Add sections only if the content justifies them.

#### Memo template

```
# Subject Line (one short line, imperative)

**To:** [Name, Role]
**From:** [Name, Role]
**Date:** [YYYY-MM-DD]

## Context
[1 short paragraph: why this memo exists]

## Decision / Update
[1-3 short paragraphs: the actual content]

## Action Items
- [Owner] [action] by [date]
- [Owner] [action] by [date]
```

**Constraints:** ≤ 2 pages, no tables of contents, no cover page, no appendices.

#### Report template

```
# Report Title (H1, cover page)

[subtitle: scope and date]

## Table of Contents
[auto-generated by Word; place a TOC field here]

## Executive Summary
[1 page max: key findings, recommendation, decision needed]

## Background
[why this report exists]

## Findings
### Finding 1
### Finding 2
### Finding 3

## Recommendations
[numbered list, each with rationale and owner]

## Appendix
[raw data, methodology, glossary]
```

**Constraints:** H1 only on the cover; H2 for major sections; H3 for sub-sections. Page numbers in the footer. TOC field updates on open in Word.

#### Letter template

```
[Sender Name]
[Sender Address]
[Sender Email] | [Sender Phone]

[Date]

[Recipient Name]
[Recipient Address]

Dear [Recipient],

[Opening: 1 sentence on why you're writing]

[Body: 1-3 short paragraphs]

[Closing: clear next step or call to action]

Sincerely,
[Sender Name]
[Sender Title]
```

**Constraints:** no headings (use bold or paragraph breaks), no tables, no TOC. Use the MD → DOCX pipeline.

#### Proposal template

```
# Proposal: [Project Name]

**Submitted to:** [Client]
**Submitted by:** [Your org]
**Date:** [YYYY-MM-DD]

## Executive Summary
[1 paragraph: problem, solution, ask]

## Problem
[what's broken or missing today]

## Proposed Solution
### Approach
### Deliverables
### Timeline

## Budget
[table: line items, totals, payment terms]

## Risks & Mitigations
[table: risk, likelihood, impact, mitigation]

## Next Steps
[what we need from the client to proceed]
```

**Constraints:** cover page is mandatory. Use the HTML → DOCX pipeline for the styled tables.

#### Minutes template

```
# Meeting Minutes — [Meeting Name]

**Date:** [YYYY-MM-DD]
**Time:** [HH:MM-HH:MM]
**Location:** [Room / video link]
**Attendees:** [Name1, Name2, Name3]
**Absent:** [Name4]

## Agenda
1. Item 1
2. Item 2
3. Item 3

## Discussion

### Item 1: [Topic]
[summary of discussion, key points raised]

### Item 2: [Topic]
[summary]

### Item 3: [Topic]
[summary]

## Action Items
| Owner | Action | Due |
|---|---|---|
| [Name] | [action] | [date] |
| [Name] | [action] | [date] |

## Next Meeting
[date, time, location]
```

**Constraints:** action items MUST be a table. Use the MD → DOCX pipeline.

### Type-mismatch warnings

If the user's request doesn't fit any of the 5 types cleanly, ask before writing:

- "Status update" — likely a memo. Confirm it's not a report.
- "Pitch deck" — wrong skill; redirect to the `pptx` skill.
- "Newsletter" — multi-section report-style; use the report template.
- "Contract" — out of scope; recommend legal review.
- "Resume / CV" — out of scope; recommend a dedicated template.

When in doubt, ask the user to confirm the type. A wrong-template DOCX takes 5x longer to fix than a right-template one.

## Typography & Page Layout

**Word documents live or die on their typography and page layout.** The MD/HTML → DOCX pipeline applies fonts and margins for you, but only if the source file is structured correctly. This section gives the values professional documents use.

### The 4-level heading hierarchy

DOCX has six built-in heading levels (H1-H6) but professional documents use only four. Anything more is a sign of a disorganized outline.

| Level | Use | Size | Weight | Color | Spacing before | Spacing after |
|---|---|---|---|---|---|---|
| **H1 — Document title** | Cover page or first body section | 24-28pt | Bold | Dominant | 0pt | 12pt |
| **H2 — Major section** | Top-level body section (Findings, Budget) | 18-20pt | Bold | Dominant | 18pt | 6pt |
| **H3 — Sub-section** | Sub-topic within an H2 | 14-16pt | Bold | Supporting | 12pt | 4pt |
| **H4 — Label** | Inline label or table header | 12pt | Bold | Supporting | 6pt | 2pt |
| **Body** | Paragraphs, lists, table cells | 11pt | Regular | Dominant | 0pt | 6pt |
| **Caption** | Source line, footer, footnote | 9-10pt | Regular | Supporting, italic OK | 0pt | 0pt |

**Rules:**

- **One H1 per document** — the document title. Repeated H1s break the navigation pane in Word.
- **H2 for major sections only** — if you have more than 6 H2s, your outline needs restructuring.
- **Don't skip levels** — H2 → H4 without an H3 looks like an error. H1 → H3 (no H2) is also wrong.
- **Use sentence case for headings** — "Findings from the Q3 review" not "Findings From The Q3 Review".

### Line spacing & paragraph rhythm

- **Body line spacing: 1.15 to 1.5.** Tighter (1.0) is for technical specs; looser (2.0) is for academic manuscripts. Business docs sit at 1.15.
- **Paragraph spacing after: 6-12pt.** Zero spacing between paragraphs creates a wall of text; 24pt+ looks like a children's book.
- **No first-line indent for the first paragraph after a heading.** Subsequent paragraphs in the same section can use a 0.25" first-line indent if you prefer, but spacing-after usually replaces the need.
- **Left-align body text.** Justified text in Word creates ugly "rivers" of whitespace and is harder to read on screen.

### Page margins & layout

| Use | Top | Bottom | Left | Right |
|---|---|---|---|---|
| Standard business document | 1.0" | 1.0" | 1.0" | 1.0" |
| Letter (formal external) | 1.0" | 1.0" | 1.25" | 1.25" |
| Report (multi-page) | 1.0" | 1.0" | 1.0" | 1.0" |
| Two-column layout | 0.75" | 0.75" | 0.75" | 0.75" |

**Default to 1.0" all around for business documents.** Letter format uses wider L/R margins for a more formal feel. Reports use 1.0" all around so tables and figures fit comfortably.

### Page break discipline

- **Manual page break before each H1 on the cover, and before each H2 that starts a new "chapter"** in long reports.
- **No widow/orphan lines** — a heading at the bottom of a page with the first paragraph on the next page is a widow. In Word: Layout → Paragraph → "Keep with next" on every H1/H2/H3.
- **Tables don't split across pages by default** — if a table is longer than half a page, decide: either keep it on one page (use the "Keep with next" option) or repeat the header row on the new page.

### Table widths

- **Tables should fit the page width** with margins to spare. Default Word table width is 100% of the text area.
- **Column widths in inches, not percentages** for stable rendering. A 3-column table inside 1" margins is 6.5" wide; split it 2.5" / 2" / 2".
- **First column often gets more space** if it holds labels (e.g., "Q1", "Q2", "Q3" as row headers in a 4-column table: 1.5" / 1.5" / 1.5" / 2").
- **Avoid cells with more than 2 lines of text.** If a cell is overflowing, restructure the table.

### Headers & footers

Every multi-page document needs a header and a footer.

- **Header (right-aligned, 9pt):** `Document Title — Page N`
- **Footer (centered, 9pt):** `[Confidentiality] | [Author] | [Date]` OR `[Page N of M]`
- **Different first-page header/footer** if the cover page should be clean (no header, no footer).
- **Page numbers in the footer** for any document > 2 pages.

### Typography anti-patterns

- **Multiple fonts in one document.** Pick one body font + one heading font. Two is the cap.
- **All-bold body paragraphs.** Bold is for emphasis, not bulk text. If a paragraph is entirely bold, the structure is wrong — make it a heading or split it.
- **Mixed font sizes in a single paragraph.** A 14pt run next to an 11pt run next to a 9pt run inside one paragraph looks broken.
- **Inconsistent margins across sections.** Pick one margin profile for the whole doc.
- **Centered body paragraphs.** Same as in slides — center is for headings and callouts only.

### Typography sanity check

Before emitting the marker, open the file in LibreOffice (or have the conversion tool emit a stats report) and verify:

- Heading levels are H1 → H2 → H3 → H4 in order (no skipped levels)
- Body line spacing is 1.15-1.5
- Page margins are 1.0" all around (or the chosen profile)
- Headers and footers are present for multi-page documents
- No mixed fonts in the same paragraph
- Tables fit within the text area (not clipped at the right margin)

If any check fails, fix the source markdown/HTML and re-emit. The DOCX is only as good as the source file.

## Pre-Emit Self-Audit (10 points)

**Run this checklist on the finished file BEFORE emitting the ◤MD_DOCX◤ or ◤HTML_DOCX◤ marker.** Every box must be ✓. If any item is ✗, fix and re-verify.

For the long-form rubric (with examples, anti-patterns, scoring), see [references/quality-checklist.md](references/quality-checklist.md).

### Content
1. **No placeholder text** — `grep -iE "xxxx|lorem|ipsum|todo|tbd|click to add"` on the source MD/HTML returns nothing.
2. **Document type is appropriate** — the structure matches one of the 5 types from *Choosing a Document Type* (memo, report, letter, proposal, minutes). A memo with a TOC is wrong.
3. **Headings are not paragraphs** — every H1/H2/H3 is a real section header, not body text styled as a heading. No skipped levels.
4. **All H1s/H2s/H3s use sentence case** — not Title Case.

### Layout
5. **Page numbers in the footer** for any document > 2 pages. Cover page can be page-numbered separately or not at all.
6. **Headers and footers are present** for multi-page documents. Single-page memos and letters can skip.
7. **No tables that overflow the page width** — every table fits in the text area with margin to spare.

### Quality
8. **Source citations present** for any data, quote, or external claim. Format: `Source: [name], [date].`
9. **XSD validation passed** — `scripts/office/pack.py` was run; no `[VALIDATE] ... FAILED` lines in the output. (The validator is on by default; see existing `### XSD Validation (Default On)` note.)
10. **Converted file opens cleanly in LibreOffice** — `soffice --headless --convert-to pdf file.docx` produces a PDF without warnings. No "missing alt text" or "unsupported element" warnings.

**If any check fails, do not emit. Fix and re-verify.** Then convert the file to PDF (or open in LibreOffice) for a visual final pass.

## Anti-Patterns Gallery

**Eight patterns that are the most common reasons an agent-generated DOCX looks bad on the first pass.** Each pattern shows the failure mode, the symptom, and a one-sentence fix. Use this gallery as a pre-emit sanity check after running the 10-point self-audit.

### 1. Wall of text

- **Symptom:** a 3-page section with no headings, no lists, no tables — just paragraphs.
- **Why it's bad:** readers skip it. The eye needs structure to track. A wall of text is also how AI-detector tools flag a document as machine-generated.
- **Fix:** break the section into H2/H3 sub-sections, or convert prose paragraphs to bulleted lists, or extract a table if there's structured data.

### 2. All-bold body paragraphs

- **Symptom:** entire body paragraphs are bold (or a single bold keyword is repeated in every paragraph).
- **Why it's bad:** bold is for emphasis, not bulk text. If a paragraph is entirely bold, the structure is wrong.
- **Fix:** make the paragraph a heading (H2 or H3) or split it into multiple paragraphs with bold only on the first 1-2 words of each.

### 3. No headings

- **Symptom:** a 20-page document with no H1/H2/H3 markers. The Word navigation pane shows nothing.
- **Why it's bad:** readers can't navigate. Screen readers can't either. The document is unusable as a reference.
- **Fix:** add an H1 for the document title, H2 for each major section, H3 for sub-sections. Use the 4-level hierarchy from *Typography & Page Layout*.

### 4. Inconsistent fonts

- **Symptom:** paragraph 1 in Calibri, paragraph 2 in Arial, paragraph 3 in Times New Roman. Or the heading is in a different font than the body.
- **Why it's bad:** mixed fonts = no design system = no trust.
- **Fix:** pick one body font and one heading font. Apply via the slide master / document styles, not per-paragraph.

### 5. Broken / overflowing tables

- **Symptom:** a table where the last column is cut off at the right margin. Or a table that splits awkwardly across pages with the header row only on the first page.
- **Why it's bad:** unreadable when printed. Looks broken on screen.
- **Fix:** reduce column count, shorten column labels, or enable "Repeat header rows" in table properties. If the table genuinely needs many columns, split it.

### 6. Missing page numbers

- **Symptom:** a 15-page report with no page numbers in the footer. A multi-page proposal where the reader has to scroll to know where they are.
- **Why it's bad:** page numbers let readers cite content and find their place. A multi-page document without page numbers is disorienting.
- **Fix:** add a footer with `<span class="pageNumber"></span>` (HTML pipeline) or use Word's Insert → Page Number. Cover page can be unnumbered or numbered separately.

### 7. Justified body text

- **Symptom:** body paragraphs use full justification (text aligned to both left and right margins).
- **Why it's bad:** justified text in Word creates "rivers" of whitespace that flow down the page. Harder to read than left-aligned.
- **Fix:** switch to left-aligned. Set in the document's default paragraph style.

### 8. Wrong document type

- **Symptom:** a memo with a table of contents. A letter with H2 sections. A proposal that's actually a memo. A status update labeled as a "report".
- **Why it's bad:** the document type is a contract with the reader. Memos are short and action-oriented; reports are long and reference. A wrong type confuses the reader about how to use the document.
- **Fix:** re-pick the type from *Choosing a Document Type* and re-structure. If the content doesn't fit any of the 5 types, ask the user to confirm.

## Creating New Documents

**CRITICAL: For rich, styled documents use the HTML pipeline.** The HTML→DOCX
pipeline (via pandoc) preserves colors, fonts, table styling, images, and layout
that the simple markdown pipeline cannot. Markdown is fine for simple text-heavy
documents but produces flat, unstyled output.

### Choosing a pipeline

| When to use... | Pipeline | Quality |
|---|---|---|
| Rich styling, charts, colors, images, custom fonts, complex tables | **HTML→DOCX** | Professional, preserves CSS |
| Simple text docs, basic headings + tables + bold only | **MD→DOCX** | Flat, Calibri 11pt, no styling |

### HTML→DOCX Pipeline (recommended for styled documents)

1. Write your document as a self-contained `.html` file to your workspace `outputs/` directory.
   Use inline CSS — pandoc will convert styles to Word formatting. Include a `<title>` tag.
2. Emit the conversion marker at the END of your reply:
   ```
   ◤HTML_DOCX◤{"html_path": "outputs/report.html", "filename": "Report.docx"}◤END_HTML_DOCX◤
   ```

The platform runs `pandoc -f html -t docx --standalone` to produce a professional
DOCX with your styling intact.

### MD→DOCX Pipeline (simple, text-only docs)

1. Write your report as a `.md` file to your workspace `outputs/` directory.
2. Emit a conversion marker at the END of your reply.
3. The platform converts markdown → styled DOCX → inline preview → user downloads.

### Step 1: Write the markdown file

Save your content to `outputs/<name>.md` in your workspace. Use standard markdown:

```markdown
# Report Title

## Section 1

Paragraph text with **bold** and normal text.

## Section 2: Data

| Column A | Column B | Column C |
|----------|----------|----------|
| Data 1   | Data 2   | Data 3   |

- Bullet point one
- Bullet point two

1. First ordered item
2. Second ordered item

> Key insight: this is a blockquote

---

*Generated on June 25, 2026*
```

### Markdown formatting rules

- `##` → Heading 2 in DOCX, `###` → Heading 3
- Tables: pipe format with `|---|---|` separator row (stripped)
- Lists: `- ` for bullets, `1. ` for numbered
- Bold: `**text**`
- Horizontal rules: `---`
- Blockquotes: `> text`

### Step 2: Emit the conversion marker

At the END of your reply, after all explanatory text, emit:

```
◤MD_DOCX◤{"md_path": "outputs/report.md", "filename": "Report_Title.docx"}◤END_MD_DOCX◤
```

The marker is stripped from visible chat. The user sees only the DOCX preview card.

### Rules

- `md_path` is relative to your workspace root
- `filename` must end in `.docx`
- Always emit the marker at the END of your reply
- The DOCX is saved to `outputs/` for persistent access
- **NEVER emit ◤DOCX◤ blocks for new documents** — they produce inferior results

### Example workflow

```
User: "Make me a monthly sales report"

Your reply:
I'll create that report now. Let me query the data.

[query database, get results]

June revenue was ¥2.3M across 847 orders. Top product: C5 Olefin at ¥890K.

[write outputs/june_2026_sales.md with full data and analysis]

◤MD_DOCX◤{"md_path": "outputs/june_2026_sales.md", "filename": "June_2026_Sales_Report.docx"}◤END_MD_DOCX◤
```

The user sees your explanation AND the formatted DOCX preview card.

## Editing Existing Documents

**Follow all 3 steps in order.**

### Step 1: Unpack
```bash
python scripts/office/unpack.py document.docx unpacked/
```
Extracts XML, pretty-prints, merges adjacent runs, and converts smart quotes to XML entities (`&#x201C;` etc.) so they survive editing. Use `--merge-runs false` to skip run merging.

### Step 2: Edit XML

Edit files in `unpacked/word/`. See XML Reference below for patterns.

**Use "Claude" as the author** for tracked changes and comments, unless the user explicitly requests use of a different name.

**Use the Edit tool directly for string replacement. Do not write Python scripts.** Scripts introduce unnecessary complexity. The Edit tool shows exactly what is being replaced.

**CRITICAL: Use smart quotes for new content.** When adding text with apostrophes or quotes, use XML entities to produce smart quotes:
```xml
<!-- Use these entities for professional typography -->
<w:t>Here&#x2019;s a quote: &#x201C;Hello&#x201D;</w:t>
```
| Entity | Character |
|--------|-----------|
| `&#x2018;` | ‘ (left single) |
| `&#x2019;` | ’ (right single / apostrophe) |
| `&#x201C;` | “ (left double) |
| `&#x201D;` | ” (right double) |

**Adding comments:** Use `comment.py` to handle boilerplate across multiple XML files (text must be pre-escaped XML):
```bash
python scripts/comment.py unpacked/ 0 "Comment text with &amp; and &#x2019;"
python scripts/comment.py unpacked/ 1 "Reply text" --parent 0  # reply to comment 0
python scripts/comment.py unpacked/ 0 "Text" --author "Custom Author"  # custom author name
```
Then add markers to document.xml (see Comments in XML Reference).

### Step 3: Pack
```bash
python scripts/office/pack.py unpacked/ output.docx --original document.docx
```
Validates with auto-repair, condenses XML, and creates DOCX. Use `--validate false` to skip.

**Auto-repair will fix:**
- `durableId` >= 0x7FFFFFFF (regenerates valid ID)
- Missing `xml:space="preserve"` on `<w:t>` with whitespace

**Auto-repair won't fix:**
- Malformed XML, invalid element nesting, missing relationships, schema violations

### Common Pitfalls

- **Replace entire `<w:r>` elements**: When adding tracked changes, replace the whole `<w:r>...</w:r>` block with `<w:del>...<w:ins>...` as siblings. Don't inject tracked change tags inside a run.
- **Preserve `<w:rPr>` formatting**: Copy the original run's `<w:rPr>` block into your tracked change runs to maintain bold, font size, etc.

## XML Reference

### Schema Compliance

- **Element order in `<w:pPr>`**: `<w:pStyle>`, `<w:numPr>`, `<w:spacing>`, `<w:ind>`, `<w:jc>`, `<w:rPr>` last
- **Whitespace**: Add `xml:space="preserve"` to `<w:t>` with leading/trailing spaces
- **RSIDs**: Must be 8-digit hex (e.g., `00AB1234`)

### Tracked Changes

**Insertion:**
```xml
<w:ins w:id="1" w:author="Claude" w:date="2025-01-01T00:00:00Z">
  <w:r><w:t>inserted text</w:t></w:r>
</w:ins>
```

**Deletion:**
```xml
<w:del w:id="2" w:author="Claude" w:date="2025-01-01T00:00:00Z">
  <w:r><w:delText>deleted text</w:delText></w:r>
</w:del>
```

**Inside `<w:del>`**: Use `<w:delText>` instead of `<w:t>`, and `<w:delInstrText>` instead of `<w:instrText>`.

**Minimal edits** - only mark what changes:
```xml
<!-- Change "30 days" to "60 days" -->
<w:r><w:t>The term is </w:t></w:r>
<w:del w:id="1" w:author="Claude" w:date="...">
  <w:r><w:delText>30</w:delText></w:r>
</w:del>
<w:ins w:id="2" w:author="Claude" w:date="...">
  <w:r><w:t>60</w:t></w:r>
</w:ins>
<w:r><w:t> days.</w:t></w:r>
```

**Deleting entire paragraphs/list items** - when removing ALL content from a paragraph, also mark the paragraph mark as deleted so it merges with the next paragraph. Add `<w:del/>` inside `<w:pPr><w:rPr>`:
```xml
<w:p>
  <w:pPr>
    <w:numPr>...</w:numPr>  <!-- list numbering if present -->
    <w:rPr>
      <w:del w:id="1" w:author="Claude" w:date="2025-01-01T00:00:00Z"/>
    </w:rPr>
  </w:pPr>
  <w:del w:id="2" w:author="Claude" w:date="2025-01-01T00:00:00Z">
    <w:r><w:delText>Entire paragraph content being deleted...</w:delText></w:r>
  </w:del>
</w:p>
```
Without the `<w:del/>` in `<w:pPr><w:rPr>`, accepting changes leaves an empty paragraph/list item.

**Rejecting another author's insertion** - nest deletion inside their insertion:
```xml
<w:ins w:author="Jane" w:id="5">
  <w:del w:author="Claude" w:id="10">
    <w:r><w:delText>their inserted text</w:delText></w:r>
  </w:del>
</w:ins>
```

**Restoring another author's deletion** - add insertion after (don't modify their deletion):
```xml
<w:del w:author="Jane" w:id="5">
  <w:r><w:delText>deleted text</w:delText></w:r>
</w:del>
<w:ins w:author="Claude" w:id="10">
  <w:r><w:t>deleted text</w:t></w:r>
</w:ins>
```

### Comments

After running `comment.py` (see Step 2), add markers to document.xml. For replies, use `--parent` flag and nest markers inside the parent's.

**CRITICAL: `<w:commentRangeStart>` and `<w:commentRangeEnd>` are siblings of `<w:r>`, never inside `<w:r>`.**

```xml
<!-- Comment markers are direct children of w:p, never inside w:r -->
<w:commentRangeStart w:id="0"/>
<w:del w:id="1" w:author="Claude" w:date="2025-01-01T00:00:00Z">
  <w:r><w:delText>deleted</w:delText></w:r>
</w:del>
```

### Images

1. Add image file to `word/media/`
2. Add relationship to `word/_rels/document.xml.rels`:
```xml
<Relationship Id="rId5" Type=".../image" Target="media/image1.png"/>
```
3. Add content type to `[Content_Types].xml`:
```xml
<Default Extension="png" ContentType="image/png"/>
```
4. Reference in document.xml:
```xml
<w:drawing>
  <wp:inline>
    <wp:extent cx="914400" cy="914400"/>  <!-- EMUs: 914400 = 1 inch -->
    <a:graphic>
      <a:graphicData uri=".../picture">
        <pic:pic>

        </pic:pic>
      </a:graphicData>
    </a:graphic>
  </wp:inline>
</w:drawing>
```

### XSD Validation (Default On)

`pack.py` runs the bundled **39 XSD schemas** against every part of the unpacked DOCX before repackaging. This catches schema violations that auto-repair can't fix (e.g., malformed relationships, missing required elements, namespace typos).

When validation fails:

```
[VALIDATE] word/document.xml: FAILED
  - Element '{...}tbl': The attribute '...' is not allowed.
  Pack aborted. Fix unpacked/word/document.xml and re-run.
```

To inspect validation manually:

```bash
ls scripts/office/validators/   # 39 .xsd files
ls scripts/office/validate.py  # the entry point
```

To skip validation in tight local iteration loops:

```bash
python scripts/office/pack.py unpacked/ output.docx --original document.docx --validate false
```

In production / headless flows, leave validation ON — it's the cheapest way to catch malformed DOCX before the LLM hands it to the user.

## Professional Output Principles

These principles apply to BOTH the `pptx` and `docx` skills. They are the shared design floor that every artifact must clear, regardless of format.

1. **Know your audience before writing.** The decision tree in `pptx` and the 4-question rubric at the top of this file are not optional — they are the first thing you read.
2. **One idea per slide / one idea per section.** A 6-word summary is the test for "one idea." If the slide/section needs more than 6 words to describe, split it.
3. **Headline not topic.** Titles are sentences, not labels. "Revenue grew 18%" not "Revenue".
4. **Source every data point.** A number without a source is unfalsifiable. Cite inline, not in speaker notes.
5. **Stay within the type's template.** A memo with a TOC is wrong. A pitch deck labeled as a report is wrong. Use the Choosing a Document Type section in this file, and the slide-type conventions in `pptx`.
6. **Pre-emit audit, then emit.** Both skills have a numbered audit (10 for docx, 12 for pptx). Run the audit; only emit if every box is ✓.
7. **Long-form rubric is the deep-dive.** Each skill has a `references/quality-checklist.md` with failure modes and copy-paste fixes. Read it the first time you generate in a new domain; skip it once the audit consistently passes.
8. **No new external lookups.** The 5 doc types, the 4-level heading system, the pre-validated contrast combos — these are opinionated defaults. Default to them; deviate only with a documented reason.
